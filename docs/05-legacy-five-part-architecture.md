# 05 · 五段式架构（历史设计存档）

> **这份文档描述的设计已不再生效。** 保留它是为了记录设计演进，以及解释场景卡里
> 那些"看起来有用但编译器不读"的字段是怎么来的。
>
> 当前生效的架构见 `03-architecture.md`。

## 当初的设计

把提示词拆成五张相互正交的卡：

| 卡 | 回答的问题 | 文件 | 现在还在用吗 |
|---|---|---|---|
| character_card | 她是谁 | `assets/character_*.json` | 部分。角色卡还在，但格式改了 |
| scene_card | 现在在什么处境里 | `assets/scenes/*.json` | 部分。只剩 `context` 字段生效 |
| relationship_state | 你们多熟 | 数据库 + `persona.STAGES` | **仍在用** |
| style_anchor | 说得符合什么规格 | `persona.STYLE_ANCHOR` | **仍在用** |
| boundary_policy | 什么情况必须怎么办 | `persona.BOUNDARY_POLICY` | **仍在用** |

**正交原则**：角色卡只写「她是谁」，场景卡只写「现在在什么处境里」，
两者不得互相引用，任意组合都要成立。做到这一点，N 个角色 + M 个场景
只需要 N + M 份内容；做不到就是 N × M 份，是维护地狱。

`persona.validate_assets()` 仍会检查这条——角色卡里出现「咖啡店」「吧台」
这类场景绑定词就报错。这个校验值得保留。

## 当初为什么要 `trait_causes`

那时角色卡只给形容词：

```
核心矛盾：待人温柔、很会照顾别人，却不习惯向别人求助
```

模型只能猜怎么演。所以改成「性格 → 成因 → 具体表达」三段：

```json
{
  "trait": "用「没关系」挡掉关心",
  "caused_by": ["小时候发现说出来也解决不了，反而让人担心"],
  "expression": "被问「你还好吗」时先说没事，停顿一下，才可能补一句真话。"
}
```

`expression` 是可执行的行为定义，模型照着演，不用猜。

**这套字段现在已从角色卡里移除。** 取代它的是 SillyTavern 风格的
`description` + `personality` + `examples`——用几条真实对话示例来定义口吻，
比结构化字段更直接。

保留的结论：**决定口吻的最大因素是示例对话，不是形容词。** 这条在现在的
架构里依然成立，而且做得更彻底。

## 当初为什么要动线和交互闸

那时的问题是：用户不说话时，她会硬找话说。

解法是 `movement_line`（把她在这一场会做的事排成有序动作节点）配合
`interaction_gate`（什么时候必须开口 / 允许沉默 / 绝对不能说），
再由编译器算出一个「本轮该说多少」的策略。

```json
{
  "id": "make",
  "action": "转身磨豆、压粉、萃取、打奶",
  "may_speak": "不说话。这一段用动作呈现"
}
```

**这套字段还留在场景卡里，但编译器已经不读了。** 当前的做法改成在
`CORE` 提示词里用散文写防重复规则（"避免重复开场、复述上一句、反复自我介绍"），
以及在 `decide_speak_policy` 里保留 `may_silent` 和 `close` 两档。

`scene_has_progressed()` 现在写死返回 `False`，场景推进机制停用。

## 如果要把它们接回来

字段都还在，接回去的成本不高。但要先想清楚两件事：

1. **设定要先统一。** 现在的 `context.situation` 写的是"你是来坐坐的，
   不默认扮演店员"，而动线里还留着"抬头看见有人进来，放下手里的抹布"。
   接回动线之前，得先定她到底是店员还是同伴，否则只会把矛盾放大。
2. **口吻示例已经能解决一部分问题。** 上线动线之前，值得先测一下
   光靠 `examples` 能把"没话找话"压到什么程度——如果够用，就不必再加一层机制。
